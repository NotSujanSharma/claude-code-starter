# claude-code-starter

A template for doing agentic programming deliberately instead of by vibes.

One main agent in one thread, coding until the context runs out, is fine until the
work gets big. Then three things break: the context window fills, nobody reviews the
code except the agent that wrote it, and there is no record of why anything is the
way it is. This repo is a structure for all three.

## The idea in four lines

1. **Plan with the human before writing code.** Questions are cheap; rework is not.
2. **Freeze the interfaces before parallelising.** Contracts are what make multiple
   agents compose instead of collide.
3. **Verify mechanically, review independently.** "Done" means a command exited 0
   and someone who didn't write it read the diff.
4. **Keep state in files.** Context windows end; files don't.

## Layout

```
CLAUDE.md              always-on rules — deliberately ~1 page
docs/
  PLAYBOOK.md          the eight phases and three gates
  DELEGATION.md        when to spawn, which model, worktree safety
  STACK.md             generated by /bootstrap — nothing here is hardcoded
  DECISIONS.md         append-only log of why
.claude/
  commands/            /bootstrap  /plan  /work  /review  /land
  agents/              scout · builder · critic · scribe
  settings.json        SessionStart hook + permission allowlist
.agent/
  plan.md              live plan
  tasks/               one file per unit of work
  contracts/           frozen interfaces
  FINDINGS.md          out-of-scope observations
scripts/
  verify.sh            the single definition of "done"
  bootstrap-check.sh   SessionStart hook; silent once configured
```

## Setup

Clone it, or copy `CLAUDE.md`, `.claude/`, `docs/`, `.agent/`, and `scripts/` into
an existing project. Then open Claude Code and say what you want to build.

**Nothing about the stack is hardcoded.** The first session detects that the repo is
unconfigured and runs `/bootstrap`, which:

1. reads whatever is already there — manifests, lockfiles, CI, existing scripts —
   so it never asks what it can find out
2. asks you the rest in one batch: what the project is, the stack, the commands,
   the conventions an agent would get wrong, and the landmines
3. writes `docs/STACK.md` and the checks in `scripts/verify.sh`
4. **runs verify to prove the commands actually work** before calling itself done

On a greenfield project it will propose a stack with reasons rather than assume one.
Re-run `/bootstrap update` whenever the project moves on.

Delete what you don't use. A structure you abandon is worse than a lighter one you keep.

## Daily use

```bash
/bootstrap
```

Then, per piece of work:

```bash
/plan add rate limiting to the public API
```

Answer its questions. Approve the design. Skim the tasks.

```bash
/work
/review
/land
```

Small change? Skip all of it and just ask. The off-ramp is part of the design.

## Model tiers

Set per task, not per project. The axis is **how completely specified the work is**,
not how complex it sounds.

| Tier | For |
|---|---|
| `haiku` | Fully specified mechanical work — renames, fixtures, drafts from an outline |
| `sonnet` | Recon, implementation against a frozen contract, tests |
| `opus` | Architecture, debugging, ambiguity, review, security, migrations |

Two overrides: the reviewer is never weaker than the author, and **debugging never
goes cheap** — a weak model on a hard bug burns ten retry loops and costs more.

## Parallelism, honestly

Parallel agents pay off for independent modules, read-only fan-out, and mechanical
bulk work. They lose whenever agent B needs to know what agent A decided.

Concurrent **readers** are always safe. Concurrent **writers** need one git worktree
each — sharing a working tree means they overwrite each other's edits. If you can't
give them separate trees, run them in sequence.

## The one metric

**Rework rate**: the share of agent-produced diffs you had to throw away. If a rule
in here doesn't move that number, delete the rule. This template is a starting
hypothesis, not a standard.
